# LoCoMo stack three-layer refactor

## Purpose

Replace the intertwined matched-stack runner with three explicit packages:

1. `code/locomo_eval/`: vendored official LoCoMo QA generation/evaluation plus one
   injected QA-recall interface.
2. `code/em_graph/`: conversation-only graph build, recall, and cache layers.
3. `code/common/`: shared model/API clients used by both packages.

The structural change is explicitly requested by the user. The three source
packages are physically grouped under top-level `code/`, alongside `data/`
and `experiments/`; their Python import names remain unchanged.
`em_graph` has no duplicated root implementation or compatibility modules:
`em_graph.__init__` is its only facade, and concrete modules live exclusively
under `build/`, `recall/`, or `cache/`.

## Constraints

- Official LoCoMo source is pinned and vendored; metric and prompt logic are
  not independently rewritten.
- `locomo_eval` knows only the QA-recall protocol, not EM graph internals.
- `em_graph` contains no LoCoMo F1/recall aggregation or answer evaluator.
- Both packages may depend on `common`; neither depends on `experiments`.
- Graph construction remains conversation-only.

`facebook/dragon-plus-query-encoder`; Memory search text uses the pinned
`facebook/dragon-plus-context-encoder`. Raw float32 CLS vectors are not L2
normalized. Raw dot products are calibrated per query by min–max normalization
over the active candidate pool before fusion; equal scores map to zero.

Raw DRAGON query artifacts use the v2 immutable artifact schema and bind the

new identity-derived path that binds the same protocol. The raw protocol
cannot use the shared L2 text cache, and any existing-path identity mismatch
fails instead of rebuilding or overwriting. Existing v1 L2 query artifacts
and v2 Memory indexes remain backward compatible.

`formal_graph.py --o2-local-dragon-diagnostic` rejects any deviation from the
locked B@25 condition before output creation. The raw query artifact must be
built from absent output/report paths with
`prepare_query_embeddings.py --embedding-model dragon --role query
--normalization none_float32_v1`. Formal retrieval then loads it read-only and
requires zero misses and zero live query-vector requests.

## Significance, dense-control, and cost tools

`significance_report.py compare` validates both formal conditions, pairs every
QA row, and applies 10,000 paired-QA and conversation-cluster bootstrap
resamples with the fixed seed `20260727`. It reports overall, Category 1–5,
local Categories 1–4, and per-conversation B-minus-A differences using only
the official serialized row metrics.

For recall analysis, an evidence-bearing row contributes its serialized
official recall and an empty-evidence row contributes zero; every QA remains
in the denominator. Raw serialized recall is retained separately, and each
condition's computed category means must exactly match its official stats.

`significance_report.py dense-control` reads both formal `run_config.json` and
prediction files, first requires the same immutable query artifact SHA-256,
then requires exact equality of every paired A/B_embed QA's ordered context-id
list. An artifact, id, or order-only difference fails.

`cost_report.py` rejects missing measurements. Cold and warm runs must each
record graph construction, entity extraction, embedding, query-entity
extraction, per-QA retrieval, and answer generation. It reports request/token
counts, wall time, latency percentiles, and graph/index/cache bytes without
estimating unavailable values. Actual cost results remain pending formal runs.

## Formal graph runner

`formal_graph.py` is the only allowed entry point for formal EM-Graph answer
runs. It requires a clean committed source tree, pinned dataset hash, absent
per-condition output directory, resolved graph/index identities, and no
resume/overwrite. It also requires `--query-artifact`: one complete,
dataset/model/role/ordered-QA/hash-bound artifact built before formal
conditions. Retrieval loads it read-only, fails on any miss, and records
query-cache usage with zero live requests. It records configuration and
graph/prompt audit before
calling the frozen evaluator, checkpoints only within the new condition,
generates official stats, and runs the external validator.

## Graph extraction and construction

Each dialog creates one Memory node. Entity extraction receives only
`text_normalized` plus optional `blip_caption`; speaker nodes are added by the
builder. Mentions edges join Entity–Memory and NEXT/PREV edges join Memories
in parsed `date_time` order. QA fields, evidence, labels, predictions, and
judge outputs are excluded. The Memory schema does not store image-search
`query` or `img_url`.

Conversation entity caches and question entity caches are physically separate.
Graph artifact identity includes the full conversation SHA-256, extraction
model/version, and normalization version. Embedding index identity additionally
includes model and memory-search-text version. Question entity keys include
sample id, QA index, full question SHA-256, extraction model, and extraction
protocol version.

## Recall and evaluation

The experiment maps each sample to `EMGraphRecall`, then passes one
`EMGraphRecallRouter` to `OfficialLoCoMoEvaluator`. The runner contains no
prompt, F1, recall, or aggregation formula. Reader context is formatted from
raw dialog text and `blip_caption`; graph embeddings use the canonical
speaker + normalized text + caption string.

System A builds only Memory/sequence nodes and performs full-pool dense recall;
it does not run entity extraction. B and its ablations use the complete EM
graph. A and B nevertheless resolve to one canonical embedding-index identity
because their Memory texts are identical; the loaded index validates every
Memory id and full text digest.

The official local QA path—not the repository's EvoEmo LLM-as-Judge—is used
here because this experiment reproduces LoCoMo's published QA protocol.
